# m-todo-backend

REST API задач и категорий на Go с SQLite. HTTP-сервер использует стандартный
`net/http`, SQLite-драйвер — `modernc.org/sqlite` (CGO не требуется).

## Запуск

Нужен Go 1.23 или новее. Команды выполняются из корня проекта:

```sh
cp .env.example .env
go mod download
go run .
```

По умолчанию API доступен на `http://127.0.0.1:8000`.

Сборка и запуск бинарника:

```sh
go build -o bin/m-todo-backend .
./bin/m-todo-backend
```

## Развёртывание на Arch Linux (systemd)

Подготовьте сервер (полное обновление Arch и установка зависимостей):

```sh
sudo pacman -Syu --needed go sudo curl
```

Нужны Go 1.23+ и работающий systemd. Запускайте скрипт из клонированной
репозитории от обычного пользователя с правами sudo:

```sh
./deploy.sh
```

Скрипт запускает тесты, собирает бинарник без CGO, устанавливает `sqlite3` через
`pacman` (пакет `sqlite`) и создаёт systemd-сервис `m-todo-backend` с автозапуском и перезапуском при
сбое. API по умолчанию слушает `127.0.0.1:8000`; фронтенд публикует его через Nginx.

- Бинарник: `/opt/m-todo-backend/m-todo-backend`.
- Конфигурация: `/var/lib/m-todo-backend/.env` — при первом запуске копируется
  из `.env.example`. Для сервера редактируйте именно этот файл.
- SQLite: `/var/lib/m-todo-backend/todos.db`. При первом развёртывании имеющийся
  `todos.db` из репозитории переносится SQLite backup API. При повторном запуске
  скрипта серверная база и конфигурация сохраняются.
- Сервис работает от пользователя `m-todo-backend`, запись разрешена только
  в `/var/lib/m-todo-backend`; используйте этот каталог для `DB_PATH`.

Обновление: `git pull` и повторный запуск `./deploy.sh`. Если меняли адрес/порт
API, передавайте URL проверки, например
`HEALTHCHECK_URL=http://127.0.0.1:9000/health ./deploy.sh`.

```sh
sudoedit /var/lib/m-todo-backend/.env
sudo systemctl restart m-todo-backend
sudo systemctl status m-todo-backend
sudo journalctl -u m-todo-backend -f
curl --fail http://127.0.0.1:8000/health
```

Для публикации фронтенда на том же сервере выполните `./deploy.sh` из репозитория
`m-todo-frontend`. При изменении порта API передайте фронтенд-скрипту соответствующий
`BACKEND_URL`.

## Конфигурация

`.env` загружается автоматически при запуске. Переменные окружения имеют
приоритет над значениями из файла. Без `.env` используются значения по умолчанию.
Локальный `.env` исключён из Git; шаблон находится в `.env.example`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | Адрес прослушивания (`0.0.0.0` для доступа извне) |
| `PORT` | `8000` | HTTP-порт |
| `DB_PATH` | `./todos.db` | Путь к SQLite относительно рабочего каталога |
| `CORS_ORIGINS` | `http://localhost:5173` | Разрешённые origins через запятую |
| `COOKIE_SECURE` | `false` | `true` для HTTPS: cookie передаётся только по защищённому соединению |

SQLite-файл создаётся автоматически, если отсутствует. Существующий `todos.db`
совместим с Go-версией: при запуске создаются таблицы, добавляются недостающие
колонки старой схемы (`urgency`, `due_at`, `category_id`) и индексы. Данные сохраняются.
Каталог, указанный в `DB_PATH`, должен существовать.

## API

### Пользователи и вход

- `POST /auth/login` — вход: `{"username":"name","password":"password"}`.
- `GET /auth/me` — текущий пользователь (`id`, `username`).
- `POST /auth/logout` — завершение текущей сессии.
- `GET /health` — общедоступная проверка работоспособности.

Имя: 3–32 символа (латинские буквы, цифры, `_`, `.`, `-`), без учёта регистра.
Пароль: 8–72 байта, хранится как bcrypt-хеш. Авторизация — через HttpOnly
SameSite=Strict cookie; сессии живут 30 дней и хранятся в SQLite в виде хешей токенов.
На HTTPS-сервере установите `COOKIE_SECURE=true` в серверном `.env`.

Все маршруты задач и категорий требуют входа (`401` без действующей сессии).
Каждый пользователь видит и меняет только свои записи. Имена категорий уникальны
внутри аккаунта. Публичной регистрации нет: пользователей создаёт администратор
через команду `create-user` на сервере.

Создание пользователя администратором (пароль передаётся через stdin):

```sh
sudo -u m-todo-backend sh -c 'cd /var/lib/m-todo-backend && /opt/m-todo-backend/m-todo-backend create-user --username name --claim-legacy'
```

Введите пароль и завершите ввод Ctrl+D. Флаг `--claim-legacy` присваивает этому
пользователю задачи и категории старой версии, у которых ещё нет владельца.
Для остальных пользователей этот флаг не нужен. Перед обновлением рекомендуется
сохранить резервную копию SQLite. Миграция сохраняет существующие задачи и связи.

### Задачи и категории

Перед curl-примерами войдите и сохраните cookie:

```sh
curl -c cookies.txt http://127.0.0.1:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"name","password":"password"}'
```

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/categories` | Категории по имени без учёта регистра |
| POST | `/categories` | Создать категорию |
| PATCH | `/categories/{id}` | Обновить категорию |
| DELETE | `/categories/{id}` | Удалить категорию, сбросив связи задач |
| GET | `/todos` | Список задач с фильтрами |
| POST | `/todos` | Создать задачу |
| GET | `/todos/{id}` | Получить задачу |
| PATCH | `/todos/{id}` | Обновить задачу |
| DELETE | `/todos/{id}` | Удалить задачу |

Фильтры `/todos`: `completed=true|false`, `urgency=low|medium|high|critical`,
`category_id=<id>`, `overdue=true|false`. `overdue=true` возвращает незавершённые
задачи с истёкшим сроком. Сначала идут задачи со сроком (по возрастанию),
затем учитываются срочность и дата создания.

Создание категории:

```sh
curl -X POST http://127.0.0.1:8000/categories \
  -b cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"name":"Работа","color":"#6366f1"}'
```

Создание задачи:

```sh
curl -X POST http://127.0.0.1:8000/todos \
  -b cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"title":"Подготовить отчёт","urgency":"high","category_id":1,"due_at":"2026-12-01T18:00:00+03:00"}'
```

У категории обязательное `name` (1–50 символов), цвет по умолчанию `#6366f1`.
У задачи обязательное `title` (1–200 символов), срочность по умолчанию `medium`.
Опциональные поля задачи: `description`, `due_at` (ISO 8601), `category_id`.
Поле `completed` меняется через PATCH.

PATCH обновляет только переданные поля. `description`, `due_at` и `category_id`
можно сбросить значением `null`. В ответах задачи содержат развёрнутую `category`
или `null`. Даты возвращаются строками, `completed` — boolean.

Создание возвращает `201`, удаление — `204` без тела. Ошибки имеют поле `detail`:
`400` — пустой PATCH или неизвестная категория задачи, `404` — запись не найдена,
`409` — повторное имя категории, `422` — неверные входные данные.
